# How the app works (for contributors)

This is a map of the project for someone opening it for the first time. The pieces every page shares (the recipe card, slot picker, toast, week calendar, the Makeable now rule, `openRecipeCard`, the pills) are in [Shared pieces](components.md): check it before building any UI. For what each screen does for a user, open **Help** in the app. For how flyer deals are read and judged, see [How the Flyers work](flyers-how-it-works.md).

## Stack

- **Frontend:** React 18 with Vite, plain CSS (`client/src/index.css`), and `@dnd-kit` for drag and drop.
- **Backend:** Node with Express.
- **Database:** Postgres through Prisma. Migrations live in `server/prisma/migrations/`.
- **Language:** every text is in both Quebec French and English (see "Languages" below).
- **Hosting:** the server also serves the built client. The README describes the Render and Neon setup.

## Run it locally

1. Make a Postgres database. [Neon](https://neon.tech) has a free one, or run Postgres yourself.
2. Create `server/.env` with these names. Use your own values and never commit this file:
   - `DATABASE_URL`: your Postgres connection string.
   - `PORT`: for example `4000`.
   - `APP_URL`: for example `http://localhost:5173`.
   - `GEMINI_API_KEY`: optional. Only flyer upload and receipt scanning need it.
   - `RESEND_API_KEY` and `EMAIL_FROM`: optional. "Forgot password" emails need both (`EMAIL_FROM` is an address on a domain verified at resend.com/domains, for example `Matt Mo Cookbook <noreply@your-domain>`). Without them the Forgot password page says it can't send emails, and an admin makes reset links instead (see "Accounts and admins"). `RESET_EMAIL_FROM`, the old name of `EMAIL_FROM`, is still read.
   - `CRON_SECRET`: optional. Only the weekly wake-up call needs it.
   - `ADMIN_EMAILS`: optional. The emails of the admin accounts, separated by commas. Only list an email that already has an account: signup refuses a listed email.
3. Install and set up the database (the very first account on an empty database signs up without an invite code; every account after it needs one, see "Accounts and admins"):
   ```bash
   npm install
   npm run setup
   ```
4. Start the server and the client in two terminals:
   ```bash
   npm run dev:server   # http://localhost:4000
   npm run dev:client   # http://localhost:5173
   ```

## Quality gates

Continuous integration (`.github/workflows/ci.yml`) runs on every push and pull request, against a throwaway Postgres:

1. `npm run build` applies every migration to a fresh database and builds the client.
2. `npm test` runs the unit tests (Vitest). This includes the language guards.
3. `npm run test:e2e` runs the browser tests (Playwright) against the built app.

While working, run only what your change touches. For example, `npx vitest run client/src/i18n` for text changes, or `npx playwright test e2e/help.spec.js` for one browser test (build first with `npm run build`). Let CI run the whole suite.

## Languages

- Every text is `t("screen.key")`. The words live in `client/src/i18n/en.js` and `fr.js`, with the same keys. Write Quebec French first.
- A name that reads the same in both languages goes under `same.*`.
- Lists of sentences (like the Help sections) are read with `dict()`.
- `client/src/i18n/i18n.test.js` fails when:
  - the two files have different keys or placeholders;
  - a French text is just English left in place;
  - a key used in code doesn't exist;
  - English is typed straight into a screen.

## Design

Screens use the Riso Poster look: paper background, ink outlines, hard shadows, and blue, pink, yellow and green accents. Colours come from the `--riso-*` tokens in `index.css`. Reuse the existing classes (`riso-chip`, `riso-btn`, `riso-eyebrow`...) before adding new ones, and add no new colours.

The grocery item is one component, `components/GroceryItem.jsx`, used by By store, By aisle, By recipe (`variant="line"`) and Store mode (`variant="store"`). Do not draw an item anywhere else. Its design is in `docs/design/grocery-item/README.md` (the handoff, with the `.dc.html` references). How many to buy is a plain number (`lib/groceryQuantity.js`); the unit only shows in the read-only recipe quantity. In a list the right side is fixed columns (sale tag or + Inventory, recipe quantity, a round number, ×) so they line up from row to row; on a phone the sale tag is not shown when the phone is held upright (no room beside the name) and, sideways, sits just left of the number like on a computer. Store mode rows show only the name and the number to buy (no meta line, no sale tag), drawn as the design's item card (a blue box that fills when checked). Every item in a view is one height: CSS sets `max(--gi-min, --gi-h)`, and `hooks/useEqualRowHeight.js` sets `--gi-h` from the view's longest name, so no name is cut.

Store mode (`components/StoreMode.jsx`, `StoreModeParts.jsx`; design: `docs/design/riso-v2-store-mode/`) is the phone's shopping view, opened from Grocery's "I'm at the store". It is one scrolling list with a section for each store (`GroceryList` passes `rows` with their `store`, in the stores' order). Each section's sticky header is a coloured sticker (`StoreSticker`) that folds the store, with a "N LEFT" badge. Above the list are a big count of what is left on the whole list and a pink progress bar. **All** (one list, no stores), **Aisle** (items under their section of the store, in walking order) and **Hide done** are three separate switches, all off at first; items are A to Z, and a checked row fades and is struck through but never moves. The sticker colours are kept on the device (`lib/storeColors.js`, localStorage `mealprep-store-colors`; the design's three stores have their colours and any other store gets a steady one from a palette), set from the Colours sheet with the colour wheel or a hex / RGB code. The light or dark theme is the shared switch (`components/ThemeSwitch.jsx`, `hooks/useTheme.js`, `lib/theme.js`): one choice kept in this browser (`mealprep-theme`, dark to begin with) that Cook mode uses too. When the last item is checked a confetti celebration starts (`StoreConfetti`, `lib/storeConfetti.js`). There is no Done button: "← List" with items checked opens a sheet to add them to Inventory. **Add to inventory** calls `onDone` (Grocery's `handleDoneShopping`), so the Inventory confirmation always opens first; cancelling it keeps the question, confirming shows an "Added to your inventory" sheet and the items leave the list. **Leave without adding** goes back to Grocery and keeps the checks; **Keep shopping** stays. **Moving an item to another store:** press and hold a row (about 200 ms, the app's one drag setup in `App.jsx`: the same `DndContext`, `PointerSensor` with a delay, `touchmove` guard and auto-scroll as the phone Planner; the row is `DraggableRow`, `touch-action: pan-y`, with the callout and text selection blocked) and drag it onto another store: its section or its sticker (`StoreDropZone`, one target for both), open or folded (a folded store stays folded). The target's sticker and section light up and the list scrolls near its top and bottom edge. While an item is carried, `DropTray` shows the stores that are not on screen (`moveTargets`, Grocery's whole store order, minus the stores in view) at the bottom, so every store can be dropped on. In All there are no stores, so there is no drag (and no hint). A drop calls Grocery's `moveToStore` (through `storeDrag.drop` in `App.jsx`'s `handleDragEnd`), the same save as dragging the item to another store on the Grocery page (by ingredient, for good), then the item is ringed in its new store and the shared Toast says "moved to X" with Undo (`onToast`, which moves it back). A tap still checks it, a swipe still scrolls, and the click that ends a drag is swallowed (`swallowClick` in `StoreMode.jsx`), so a drag never checks the row. The hint under the toolbar explains the drag and shows only with more than one store.

The Inventory item form is one component, `components/InventoryItemForm.jsx`, for both "+ Add item" and a tapped item card (`mode="add" | "edit"`). Its design is in `docs/design/inventory-item-form/README.md`; its logic (dates and days, the expiry tag and line, fallback shelf life, amount steps, what gets saved) is in `lib/inventoryForm.js`. Add goes straight to Inventory, because typing an item in Inventory's own form counts as confirming it; every other way of adding still uses the confirmation sheet, except the finished view's Leftovers card (see `CLAUDE.md`). Its Leftovers mode (the Leftovers chip, or the Leftovers shelf's +) adds leftovers by hand: portions, Fridge or Freezer with the leftover keep times, and the recipe they're from. Edit works on a copy and saves only with Save changes. The server gives the form USDA shelf life for every shelf (`/pantry-inventory/suggest`) and the Recent chips (`/pantry-inventory/recent`).

Buttons press in for a moment (under 150 ms) through one shared rule in `index.css`, next to `.riso-btn`: `riso-btn`, `riso-chip`, `riso-filter-chip`, the Grocery and Store mode buttons, and anything with `riso-press`. A new kind of button joins by using one of those classes or by being added to that list. The global reduced-motion rule turns the animation off. Step timers (the recipe card and Cook mode) share `hooks/useStepTimers.js`.

Cook mode (`components/CookMode.jsx`, `CookModeParts.jsx`; design: `docs/design/riso-v2-cook-mode/`) is the full-screen step view opened from a recipe card's "Start cooking": a step rail, the step (split into short paragraphs for display only by `lib/stepParagraphs.js`), "For this step" rows, a timer card and a bottom bar, on a computer in three columns and on a phone in one, light or dark. A recipe whose ingredients have prep notes ("diced") opens on a **Before you start** page first (design: `docs/design/riso-v2-cook-mode-prep/`; `lib/cookPrep.js` works out the groups, how lines, step tags and the preheat sentence from the recipe's own notes and steps, with no AI and nothing saved). Which ingredients a step uses is one matching, `stepIngredients` (`lib/ingredientMatch.js`), shared by "For this step" and the prep page. `docs/components.md` has the details (layout, the fitting of long steps, the dark tokens, what closing does). Its last step's "I cooked this" opens the finished view below.

"I cooked this" (« Je l'ai cuisiné ») opens one finished view (`components/CookedView.jsx`, `CookedViewParts.jsx`; design: `docs/design/riso-v2-cook-mode/`, Cook Mode Finished) from three places: the end of Cook mode (full screen), a planned meal's card on the Planner and tonight's meal on Home (a sheet). `App.jsx` hosts it (`openCooked`). Leftovers come first: the card shows the LEFTOVER item it adds and is the confirmation (`CLAUDE.md`). Then "Take out of your Inventory" reviews what the recipe used: each ingredient's Inventory item (`lib/inventoryMatch.js`, both languages) and the amount, scaled and converted, editable, asking when units don't convert. "Remove from inventory" takes the amounts out through `POST /api/pantry-inventory/take-out` (items at zero leave), and the meal is marked cooked (`PlannerEntry.cookedAt`), so it leaves the grocery list. One Undo puts everything back (`POST /api/pantry-inventory/put-back`).

Leftovers are one system (`lib/leftovers.js`, `PantryInventoryItem.isLeftover` and `recipeId`): LEFTOVER items on Inventory's Leftovers shelf, counted in portions, kept in the fridge or freezer with one set of keep times, each with a use-by that is a Quebec calendar day (`lib/quebecDay.js`; days left count Quebec days, not hours); the Planner search plans them (`PlannerEntry.leftoverItemId`, nothing on the grocery list); when a planned leftover's day has passed, `POST /api/pantry-inventory/leftovers/settle` (called when the app opens) takes one portion off, once, and the toast has Undo. `docs/components.md` has the details (Finished view, Ingredient-to-Inventory matching, Leftovers).

## Accounts and admins

- An account is a `User` row: the email (trimmed and lowercased), a bcrypt hash of the password, the language, the weekend settings, the signup date (`createdAt`), `role` and `lastActiveAt`.
- Logging in creates a `Session` row that lasts 30 days and sets an httpOnly `session` cookie (SameSite Lax, secure in production) that holds only the session's id. `requireAuth` (`server/src/lib/auth.js`) reads it in front of every data route and attaches `req.userId`, or answers 401. It also records `lastActiveAt`, at most every 15 minutes per account.
- **Admins:** only `ADMIN_EMAILS` makes an account an admin. `requireAdmin` (`server/src/lib/admin.js`) checks it on every `/api/admin` call and answers 403 to everyone else. `User.role` records the last check and never grants admin on its own. Signup refuses a listed email, so an email listed before it has an account can't be claimed by someone else; the server logs a warning at startup for each listed email with no account.
- **Signup is invite-only.** `POST /api/auth/signup` needs an `inviteCode`: a code Matt made in Admin (Invite codes). A code (`InviteCode`: `code`, an optional `note`, `maxUses`, `usedCount`, `expiresAt`, `active`) works while it is switched on, has uses left and hasn't expired (`inviteState` in `server/src/lib/invites.js`). Codes are 8 letters and digits written `K7M2-QX9P`, without look-alikes (no 0, O, 1, I, L), and are read however they are typed (capitals, spaces and the dash don't matter). Spending the code and making the account are one transaction, and the spend is one conditional update, so two signups can't both take the last use and an account that fails to be made keeps the code's use. The code is checked before the email, so a visitor without one learns nothing about who has an account. Each refusal has its own message (missing, unknown, used, expired, switched off), in both languages. `User.inviteCodeId` records which code an account joined with. **The one exception** is the very first account on an empty database (a new install or a local one): there is nobody yet to make a code, and no admin until that account exists. Login never asks for a code, so accounts made before invite codes keep working.
- **Admin endpoints for codes** (behind the same guard): `GET /api/admin/invites` (newest first, with the emails that joined with each), `POST /api/admin/invites` (`note`, `maxUses` 1 to 100, `expiresInDays` 1 to 365 or none; the server picks the code), `PATCH /api/admin/invites/:id` (`{ active }`, to switch a code off or on; accounts already made with it stay).
- **Password reset.** A reset link is a `PasswordResetToken` row whose id is the secret: it works once and expires after 1 hour. Using it (`POST /api/auth/reset-password`) sets the new password, marks the link used and signs the account out everywhere. Links are made one way (`server/src/lib/resetLink.js`) by three things:
  - **The Reset link button** in Admin → Members (`POST /api/admin/members/:id/reset-link`, behind the admin guard, so a non-admin gets 403). It replaces any link the member hadn't used yet and answers with the link, which is shown under the member with Copy. The link is not stored anywhere an admin can read it back. The server logs who made one for whom, never the link. This is how a friend resets a password during the beta, while no email can be sent.
  - **`npm run reset-link -- <email>`** (`server/src/scripts/resetLink.js`), run from Render's Shell, for when no admin can log in. It makes the same link the same way and prints it. For an email with no account it prints only "No such account." Every use is logged on one line with the time and the email, in the Shell (Render's Logs tab doesn't show commands run in a Shell).
  - **The "forgot password" email** (`POST /api/auth/forgot-password`). It answers `{ sent, message }` and never says `sent: true` unless an email really went out. Email goes out through the one sender in `server/src/lib/mailer.js`, from `EMAIL_FROM`; there is no built-in sender, because Resend's own test address only delivers to the Resend account's owner. If `RESEND_API_KEY` or `EMAIL_FROM` is missing, the route answers `sent: false` for every email typed, decided before any account is looked at, and logs why. If Resend refuses a send (an unverified domain, testing mode, an outage) the server logs Resend's reason, deletes the link it just made and answers `sent: false`; that failure is remembered for 10 minutes (`EMAIL_FAILURE_MEMORY_MS`), and for that time everyone gets `sent: false` without another try, so the answer doesn't depend on which emails have an account. The one gap: the first request that hits a failure is the only one that can tell an email with an account from one without. The page says "We can't send emails yet. Ask Matt for a reset link." The "sent" answer is the same whether or not the email has an account. A repeat within 2 minutes doesn't send a second email (kept in memory, counting only emails that went out, so a link made in Admin never stops one).
- **A daily limit on Gemini readings.** The only two routes that call Gemini, `POST /api/flyers/upload` and `POST /api/receipts/parse`, share one count per account per day (`AiUsage`, one row per account and day). The limit is `AppSettings.aiDailyLimit`, which Matt sets in Admin (AI usage); with no row it is 10 (`DEFAULT_AI_DAILY_LIMIT`), and 0 pauses reading for everyone. A day is the Quebec calendar day (`America/Toronto`, from `server/src/lib/quebecDay.js`, the one Quebec day the app uses), so the count starts again at local midnight. `takeAiUse` (`server/src/lib/aiLimit.js`) takes a reading just before Gemini is called, after the file passed its checks, with one conditional update so a burst of requests can't get past the limit; at the limit the route answers 429 with `aiLimit` (or `aiPaused` at 0), in the reader's language. The reading is given back only when Gemini could not answer on its own side (our key refused, busy, down, the connection dropped: `shouldGiveBack`); a file Gemini rejected still counts. The limit is the same for admins. Flipp imports and the weekly cron don't call Gemini and aren't limited. `GET /api/admin/ai-usage` lists each account's use today and `PUT /api/admin/ai-limit` changes the limit.

## Weekly flyer import

The server checks hourly while awake and imports on Thursdays. A GitHub Action (`.github/workflows/flyer-import.yml`) wakes a sleeping free-tier server on Thursday and Friday. The details, including the secrets the action needs, are in the README and in [How the Flyers work](flyers-how-it-works.md).
